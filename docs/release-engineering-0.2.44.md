# 0.2.44：本机响应的连接收尾

## 问题与复现

上轮全量回归中的统一服务测试出现 `ConnectionAbortedError / WinError 10053`，
当时单独复测未复现。本轮进一步拆分请求头和正文的发送时序，确认了一个真实的
响应交付问题：权限检查已拒绝请求，但服务立即完全关闭连接；稍后到达的正文可能
触发 TCP 重置，使客户端读不到已经发送的403响应。

同一本机的100次拥有的合成请求中，修复前出现55次连接中止；相同请求和发送时序
在修复后均得到完整403正文。这是特定环境的复现证据，不是所有机器的故障概率。
记录位于本机 `dist/http-rejection-before.log` 与 `dist/http-rejection-after.log`。

HTTP 标准描述了这类重置覆盖响应缓冲区的问题，并说明可分阶段关闭连接。
依据：[RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6)。
Python 的关闭方向语义参见 [socket.shutdown](https://docs.python.org/3/library/socket.html#socket.socket.shutdown)。

## 实现与边界

统一工作台、研究入口和专业工作台复用同一个本机请求处理层。响应明确声明
`Connection: close`，刷新输出后先关闭写方向，再受限地读弃后续数据，最后释放连接。
超出连接名额时的503响应采用相同收尾方式。

读弃最多64 KiB，绝对期限100 ms；每次读取最多8 KiB，不把整份正文存入内存。
持续滴入数据不能刷新这项期限。客户端已经关闭、超时或连接已不可用时直接结束，
以现有清理逻辑关闭流并归还连接名额。未完成请求头仍受原有绝对期限约束。

丢弃过程不解析 JSON，不调用业务操作，也不处理后续流水线请求。拒绝权限、来源、
路由、内容类型或大小的决定仍在原处作出；读弃只发生在回复之后，不等待请求声明
的完整正文长度，不占用项目动作锁。跨项目上下文、人工决定和请求去重机制保持原有
约束。此处没有引入客户端自动重试，连接错误仍不能作为操作未发生的证明。

时间和大小上限意味着无法保证任意慢速或无限发送客户端都收到最后响应。这是有界的
本机连接收尾，不是互联网生产服务、持久连接或完整 HTTP/1.1 服务的实现。

## 验证

真实回环请求覆盖工作台和研究两个入口、独立专业工作台、分段到达的正文，以及403、
404、413、415的完整错误正文。检查拒绝时不进入 JSON 正文读取，不改变项目选择；
带合法凭据的第二条流水线请求也不会在拒绝后执行。

资源检查覆盖总丢弃字节数、单次读取上限、滴入客户端的绝对期限，以及不完成声明
正文的连接不会持续占用名额。已有来源验证、请求头歧义、大小限制、跨标签页与跨项目
保护继续回归。浏览器验证错误显示、项目操作和草稿流程，保留相应响应证据。

发行运行时自检新增 `http-teardown`：实际发送延迟到达的未授权正文，检查完整403及
当前项目不变，合计36项。全量与相关专项结果分别记录，不将重跑成功抹去历史失败。

Windows 3.10和3.14的远端记录均出现过全量测试已通过、安装验收触及30分钟上限。
CI 将每个 Windows 环境的普通 unittest 发现结果按条目顺序分成两组，Ubuntu 仍执行
完整一组。所有条目，包括跳过项和导入失败项，都恰好归入一组；不按耗时或通过情况
筛选。每组保存发现摘要和测试 ID 清单，空分组不能作为成功任务。安装与发布检查保留。
