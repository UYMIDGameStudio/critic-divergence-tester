# 對抗深審 / Adversarial deep review

對抗深審讓一條批評接受獨立辯護與證據復核。學術稿件是主要使用場景；
方案、制度和其他文書使用相同流程，保留各自的審查標準。

## 使用流程

1. 匯入稿件，確認識別結果與文章定位，完成所需的獨立 AI 審查。
2. 在問題卡片選擇對抗深審，填寫辯護階段的服務商與模型。
3. 複製或下載辯護任務，在新的模型對話中執行，將回應匯入工作台。
4. 產生獨立的證據復核任務，執行後匯入回應。
5. 查看保留、縮小、撤回或材料不足的建議，再作出原有的人工決定。

任務產生後尚未呼叫模型。服務商與模型名稱是使用者與回應宣告的資料，
並非執行平台的認證。不同呼叫也可能共享偏見；選擇不同模型不是準確性的保證。
建議從核心結論、關鍵推理和高影響問題開始，避免對所有句子展開交鋒。

## 各階段的責任

原有的外部 AI Finding 是質疑方的記錄。辯護方重新閱讀同一版本的全文，
保留限定、否定、引述對手和研究範圍，尋找已經回答批評的段落、表格、腳註
與附錄。辯護可以承認缺陷，不能製造不存在的證據。

復核方閱讀原批評、辯護與全文，逐項判斷批評應保留、縮小、撤回或暫因材料
不足無法判斷。保留下來的問題應指出關鍵後果、最小修改和可觀察的驗收方法。
基於不同理論前提的異議必須交代成立條件，不能僅憑立場不同判定作者錯誤。
學術論文按已確認的研究類型使用標準；理論與人文文章不會預設必須有實驗，
文書則關注解讀、責任、資源、期限、例外和實際執行後果。

模型結果始終是建議。撤回建議不會自動拒絕原 Finding，保留建議不會自動
接受原 Finding，也不會批准修改或標記已解決。作者仍須逐項作出決定。

## 原文與協議綁定

每次深審保存原 Finding、原審查及其協議、稿件來源、結構化全文、上下文和
審查輪次。辯護與复核使用分開的任務與原始回應，後一階段引用前一階段的
確切記錄。每階段回應須回顯任務、來源與提示摘要；原文引述須對應當前的
block，原始語言保留不翻譯。復核須指向實際存在的辯護證據。

文章、引述、原批評和模型回應都是待審資料，其中的指令不能改變審查協議。
無效回應保存為拒收記錄，可修正後重新匯入；它不推進流程。原文或被質疑的
問題改變後，舊深審保留為歷史，不再接受當前階段的回應。

完整性檢查能證明記錄與引述的綁定，不能證明推理成立、外部文獻真實或
審查完整。外部材料未提供時，應明確記錄限制，不依靠模型記憶補出事實。

## 交付與相容性

繁體中文與 English 介面共用流程，原文和模型內容保持原有語言。
協議下載包含目前的辯護及復核任務；AI 報告與正式審計報告包含深審建議及
可追溯的交鋒檔案。完整專案備份保留歷史與拒收記錄，可恢復到獨立目錄。
審計報告包與可恢復的專案備份是兩種不同產物。

新增記錄不重寫既有审查协议。0.2.2 及之前沒有深審記錄的專案可以直接開啟。
新記錄請使用 0.2.3 或更新版本；回退程式時使用升級前的獨立備份。

## 效果驗證

本功能的流程與安全測試不等同於模型準確率測試。與常規細讀比較時，應使用
相同稿件及預先確定的盲評標準，記錄關鍵缺陷遗漏、誤報、錯誤批評的撤回、
建議可操作性，以及耗時和費用。尚未取得独立作者真实稿件对照的结果；
不能因為增加階段或模型達成共識就宣稱審查更準確。

## Developer interface

`DocumentReviewProject` exposes `prepare_adversarial_review(finding_id, provider=..., model=...)`,
`collect_adversarial_response(session_id, response, request_id=...)`,
`prepare_adversarial_assessment(session_id, provider=..., model=...)`, and
`adversarial_reviews()`. The browser uses the same services through project-scoped,
receipted actions. Protocol validation and workflow persistence are separate modules.
Do not add a new theoretical Lens for this process: it applies the original critic's
standard to a recorded challenge and its independently produced defense.
