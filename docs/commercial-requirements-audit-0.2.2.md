## 实质缺口与下一步

### F0：人工确认界面的具体风险，本轮已修复

原 `studio_web/research_product.js:122` 的复查表单总把 `resolved` 放在最终状态
第一项，未按模型建议或既有人工决定初始化。模型写 `unresolved` 或
`partially_resolved` 时，用户只填理由、点击保存，即可归档为人类 `resolved`。
原 L172–177 会直接提交这个默认值。领域服务按显式状态保存，不能识别用户未选择的 UI 默认值。
这削弱了 D28、D43–46 的人工确认与来源区分要求。

本轮 `studio_web/research_product.js:115` 的 `resolutionCard` 和 L119 的绑定逻辑
改为：未决定时状态为空，未选状态或未填理由时禁止保存，处理器再次校验；已有人工
`final_status` 和理由回显；模型证据与未确认事项同时展示。切换语言后重新计算按钮状态。

实际 Chrome 152 验证进入真实复查阶段，模型建议为未解决/部分解决时均不默认成为
已解决；保存、刷新、两种语言切换后旧决定保留，最终导出仍为 `unresolved` 和
`partially_resolved`。该风险已获得工程修复证据；“用户是否理解并能正确裁决”仍由 F1/F3 验收。
