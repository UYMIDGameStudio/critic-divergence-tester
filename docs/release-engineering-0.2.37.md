# 0.2.37：正文质量门与修改恢复

## 修复的问题

此前，非零字节但只有空白的文件能够确认识别、运行本地预检，并导出零 Finding 的正式
报告。只有空单元格的 CSV 能通过确认，但运行表达预检时可能因证据为空而报错。
图片占位、页眉页脚等辅助内容也可能被当作足够的审查输入。

本版用共同的 `has_reviewable_text` 判断检查实际文字。段落、标题、列表、引用和表格
单元格中的可见文字均可满足条件；容器、图片占位、分页及页眉页脚不代替正文。
纯空白和 Unicode 格式、控制标记不算实际文字。没有人为规定最低字数、单词数、语言
或字母比例；短文本、数字和符号也可进入后续人工确认。这项检查只判断有无正文，
不证明全文完整提取、内容充分或审查质量合格。

## 确认、审查与历史记录

没有正文时，普通确认与带警告继续均不能通过；人工修正也须解析出实际正文后才保存。
新上下文确认、本地预检、AI 审查、协议、修改任务及正式导出共同遵守这条边界。
已有复审轮次时，检查当前轮次的文档，不借用原始版本的正文作为凭据。

界面保留预览、原件、修正识别和更换文件入口，用繁中、英文说明原因。已经确认上下文
或留下审查历史的旧空项目不会自动改写；重新导入原件并选择「重新解析為新專案」，
在新项目补充正文后重新确认。旧产物仍为历史记录，本版不会撤回过去下载的文件。
缺少 OCR 或 PDF 渲染器的现有限制继续执行，不能用这次检查替代这些限制。

## 修改提案的恢复路径

所有批准项合并后，如果修改稿不再有正文，系统在写入 Revision、运行复审前停止。
过去已生成的空修改稿也不能作为新的正式修改稿导出。失败不会留下部分修改稿或改变
先前的提案、批准、事件、收据和原件。

在生成修改稿之前，可展开「調整修改操作」重新明确操作类型。旧 Hunk 与原批准保留，
操作改变后旧绑定失效，必须提交并批准新提案。非删除的已批准提案还提供
「編輯並重新提交這一項」，保留当前文字供编辑。新提案取得独立标识，不能继承旧批准。
文本来源选择在重新编辑、驳回与操作变更后仍可核对，避免把 AI 辅助来源默认变成人工
撰写。已经生成的修改稿保持不可变，后续工作仍遵守既有复审与轮次流程。

## 验证

合成文件覆盖空白、不可见格式标记、空表格、图片占位、仅页眉内容、八种语言的极短
文字、数字与符号。测试同时检查有效表格正文可用，避免用字数阈值代替语义判断。
失败确认和修正核对整个项目字节不变；真实修正能够恢复到本地预检。

历史夹具以旧行为生成有效收据与零问题导出，再验证新的操作被拦截、历史不改写。
批准删除或格式标记替换导致空正文时，核对失败无写入；改为有正文的新提案后必须再次
批准，才可生成和导出。历史空 Revision 的再导出也执行同一检查。

浏览器执行空 CSV 识别、繁中桌面和英文320宽度提示、修正失败与恢复、本地预检、
人工裁决、批准删除、拦截空稿、调整操作、重新提案、再次批准、编辑已批准文字及正式
导出。核对原始字节与旧 Hunk 未改动。发行自检增加 `reviewable-text`，包含完整恢复
路径。商业试用和模型准确率仍需各自的实证验收，不能由这组工程测试代替。
